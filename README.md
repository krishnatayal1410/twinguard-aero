# TwinGuard Aero

**Mission-Aware Hybrid Physics–AI Digital Twin for Aero-Piston Engines in MALE UAVs**

TwinGuard Aero is an SIH26054 proof-of-concept for continuous aero-piston-engine health monitoring, degradation diagnosis and mission-level decision support.

The system is designed around one operational question:

> **Given this engine's current condition and the remaining mission profile, how much risk does continuing the mission create, why, and what lower-stress alternative can be evaluated?**

TwinGuard is not just a telemetry dashboard and the 3D engine is not the digital twin by itself. The twin is the synchronized state, expected-behavior model, residual history, sensor-trust assessment, diagnostic state, health indices, degradation trend, RUL estimate and mission-reliability model operating together.

The included simulator, healthy-reference equations, health weights, diagnostic confidence, RUL and mission-risk calculations are prototype engineering logic. They require engine-specific calibration and authorized test-rig/ECU validation before any operational use.

Any ML metric generated by `ai/train_models.py` is a **synthetic proof-of-concept metric only**. It must never be presented as real MALE-UAV engine validation.

# 2. Twin layers

## Real-Time State Twin
Maintains the latest synchronized engine state from telemetry including RPM, throttle, CHT, EGT, oil pressure, oil temperature, fuel flow, vibration, electrical signals, altitude, ambient conditions, timing and operating hours.

## Hybrid Physics–Diagnostic Health Twin
Calculates context-dependent expected behavior and residuals:

```text
Residual = Observed value - Expected healthy value
```

The current physics layer is intentionally a **generic low-order aero-piston surrogate**, not an OEM performance map.

## Mission Reliability Twin
Combines current engine health, RUL margin, degradation rate, persistent diagnostic evidence and planned mission stress to generate:

- overall mission-risk class,
- Mission Feasibility Index,
- post-mission health projection,
- post-mission RUL projection,
- dominant risk factors,
- a rescored lower-stress alternative.

The Mission Feasibility Index is an engineering decision-support score, **not a calibrated probability of mission success**.

## Evidence / Replay Twin
Stores and presents the evidence behind decisions:

- residual spectrum,
- sensor trust,
- subsystem health,
- temporal degradation,
- diagnostic confidence,
- mission-risk contributors,
- replayed mission events.

| Signal | Unit / interpretation |
|---|---|
| RPM | rev/min |
| Throttle | % |

| EGT | °C |
| Oil pressure | bar |
| Oil temperature | °C |
| Fuel flow | L/h surrogate |
| Vibration | g RMS surrogate |
| Battery voltage | V |
| Alternator voltage | V |
| Altitude | m |
| Ambient temperature | °C |
| Injection/ignition timing | degree proxy |

The unit names are intentionally explicit to prevent frontend/backend/simulator mismatches.

# 4. Synthetic fault scenarios

The simulator supports progressive rather than instantaneous fault injection:

- `normal`
- `lubrication`
- `overheating`
- `cooling_degradation`
- `vibration`
- `sensor_drift`
- `injector`
- `misfire`
- `combustion_instability`
- `alternator_degradation`

Fault severity ramps toward the operator-selected target so the demo can show **degradation developing over time**.

The repository deliberately does **not** use turbine-blade/turboshaft failure modes because SIH26054 targets aero-piston engines.

---

# 5. Sensor Trust

Sensor Trust is intentionally separated from engine health.

A large residual does not automatically mean a sensor is bad. TwinGuard evaluates whether the abnormal channel is corroborated by related signals and whether it changed implausibly quickly.

Example:

```text
Oil pressure abnormal
+ oil temperature rising
+ vibration rising
→ likely physical lubrication condition
→ sensor trust can remain relatively high
```

versus:

```text
Oil pressure suddenly abnormal
+ oil temperature normal
+ vibration normal
+ other physics inconsistent
→ possible isolated sensor problem
→ oil-pressure sensor trust decreases
```

# 6. Temporal intelligence

The twin tracks short-window rates such as:

- oil-pressure change/min,
- oil-temperature change/min,
- CHT change/min,
- EGT change/min,
- vibration change/min,
- battery/alternator change/min,
- health-index change/min,
- anomaly persistence samples.

This lets the diagnostic layer distinguish a single abnormal sample from a worsening condition.

# 7. AI / ML model policy

TwinGuard has two diagnostic paths.

## Engineering fallback

The default stable path uses transparent residual, trend and multi-signal rules. It is always available and is explicitly reported as:

```text
ENGINEERING_FALLBACK
```

## Native synthetic ML

`ai/train_models.py` can train:

- Isolation Forest anomaly detector,
- XGBoost synthetic fault classifier,
- XGBoost synthetic RUL regressor.

The runtime validates both:

- `models/feature_order.json`
- `models/fault_labels.json`

before loading packaged artifacts. Stale or incompatible models are rejected rather than silently producing incorrect labels.

See `models/MODEL_CARD.md`.

To enable a compatible retrained XGBoost pack:

```bash
export TWINGUARD_NATIVE_ML=1
```

Do not enable it until the model pack has been retrained on the current `aero-piston-v2` contract.

# 13. Security boundary

The proof-of-concept includes:

- local Sign Up / Sign In / Sign Out,
- PBKDF2-SHA256 password hashing,
- expiring server-side sessions,
- protected operator APIs,
- separate telemetry ingest key,
- explicit CORS allowlist,
- trusted-host validation,
- request-size limit,
- security response headers.

This is not defence-grade cybersecurity. Operational deployment would require appropriate identity, TLS/mTLS, managed secrets, network segmentation, auditability, dependency/security testing and aerospace/defence security review.

---

# 14. What must happen before real-engine use

A credible next validation phase requires:

1. identify the target aero-piston engine and authorized operating envelope,
2. obtain ECU/test-rig telemetry and channel definitions,
3. calibrate the healthy expected-behavior model or performance maps,
4. validate sensor units and sampling rates,
5. collect known normal/transient/fault cases,
6. establish degradation and maintenance ground truth,
7. calibrate uncertainty and false-alarm behavior,
8. validate RUL against real degradation history,
9. validate mission-risk logic with domain experts,
10. complete safety, cybersecurity and deployment assurance.

Until then, TwinGuard should be presented exactly as what it is: **a working architecture and synthetic Digital Twin demonstrator showing how engine state can be translated into explainable mission-level reliability intelligence.**
