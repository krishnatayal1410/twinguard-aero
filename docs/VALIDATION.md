# TwinGuard Aero — Validation Status

## Scope

TwinGuard Aero is currently validated as a **software and synthetic Digital Twin proof-of-concept**. It is not validated as a real-engine airworthiness, maintenance-certification or autonomous flight-safety system.

The current codebase is intended to prove that the following architecture can operate coherently end to end:

```text
Telemetry → Expected State → Residuals → Temporal Trends
→ Sensor Trust → Diagnostic Hypothesis → Health / RUL
→ Mission Reliability → Explainability / Replay
```

## Automated backend tests

`backend/tests/test_pipeline.py` now checks:

- end-to-end Digital Twin state generation,
- six subsystem/sensor health outputs,
- explicit synthetic/model provenance,
- mission-risk directionality,
- lubrication degradation behavior,
- physical-fault-vs-isolated-sensor trust behavior,
- alternator and injection-timing residual channels,
- removal of the old turboshaft/turbine-blade fault taxonomy.

Run:

```bash
export PYTHONPATH="$PWD/backend"
pytest -q backend/tests
```

The repository should only report a fresh pass count after those tests are actually executed on the current branch/environment.

## End-to-end verifier

`scripts/verify_system.py` checks a running stack for:

- backend health,
- authentication,
- synchronized Twin state,
- `generic-aero-piston-surrogate-v2` model identity,
- temporal trends,
- diagnostics,
- system status,
- maintenance output,
- Mission Reliability Twin output,
- progressive lubrication-fault observability,
- mission replay.

Run after the simulator/backend/frontend stack is running:

```bash
python scripts/verify_system.py
```

## Fault-matrix validation

`scripts/validate_fault_matrix.py` exercises:

- normal,
- lubrication degradation,
- overheating,
- cooling degradation,
- abnormal vibration,
- sensor drift,
- injector abnormality,
- misfire,
- combustion instability,
- alternator degradation.

Fault injection is progressive, so the script allows scenarios to develop before recording the final diagnostic state.

## Model artifacts

The repository may contain model files produced by an earlier synthetic feature/fault contract. The current runtime deliberately compares `feature_order.json` and `fault_labels.json` against the active `aero-piston-v2` contract before loading them.

If artifacts are stale or incompatible:

```text
model_state = ENGINEERING_FALLBACK
```

and the UI exposes the compatibility warning.

To generate a new compatible synthetic pack:

```bash
bash scripts/train_models.sh
```

or:

```bash
python ai/train_models.py
```

The retraining script generates:

- `anomaly_model.joblib`
- `fault_model.joblib`
- `rul_model.joblib`
- `fault_labels.json`
- `feature_order.json`
- `synthetic_metrics.json`
- `model_manifest.json`

## Synthetic metrics

Any classifier/RUL metrics produced by the training script are derived from synthetic data generated by the same proof-of-concept family of assumptions.

They can be used for software/model-development comparisons, but they **cannot** establish:

- real fault-detection accuracy,
- real false-alarm rate,
- real RUL accuracy,
- real MALE-UAV mission reliability,
- certification or operational readiness.

Do not copy older synthetic metrics into SIH material as if they describe the current `aero-piston-v2` model. Retrain first, record the exact code/manifest, and label the result synthetic.

## Digital Twin validation currently available

The healthy simulator and expected-state model intentionally share a coherent low-order relationship so software behavior can be exercised under known conditions.

Useful current checks include:

- residuals remain comparatively stable in a healthy synthetic scenario,
- injected degradation causes expected residual directions,
- multi-signal faults reduce the appropriate subsystem health,
- isolated sensor inconsistency lowers measurement trust more than corroborated physical degradation,
- progressive faults increase temporal evidence/persistence,
- more stressful mission profiles produce higher decision-support risk,
- lower-stress counterfactual profiles are independently rescored.

These are **scenario-consistency tests**, not real-aircraft validation.

## 3D visualization

The current engine visualization is a procedural horizontally-opposed aero-piston representation built from WebGL/Three.js geometry.

It includes conceptual modules for:

- cylinder banks,
- crankcase / rotating core,
- lubrication,
- fuel / induction,
- exhaust / thermal path,
- electrical / alternator.

It is intended to communicate Twin state and affected subsystems. It is not proprietary manufacturer or DRDO CAD and is not used as the physics model itself.

## Required next validation tier

Before operational claims, TwinGuard requires target-engine-specific evidence such as:

1. authorized ECU/test-rig signal definitions and units,
2. calibrated healthy operating maps across RPM/load/altitude/environment,
3. known transient behavior,
4. known fault and degradation cases,
5. maintenance/failure ground truth,
6. sensor accuracy and failure-mode characterization,
7. run-to-failure or equivalent prognostic evidence,
8. uncertainty calibration and out-of-distribution testing,
9. false-positive / false-negative analysis,
10. mission-risk validation with relevant domain experts,
11. deployment, cybersecurity and safety assurance.

Until that evidence exists, the correct description is:

> **A working synthetic hybrid Digital Twin demonstrator for explainable aero-piston-engine health and mission-reliability research.**
